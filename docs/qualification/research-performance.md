## 输入与测量约定

- 仅使用脚本生成的确定性合成 TDX 日线字节。日期从 1990-01-01 起逐日排列，包含周末；20,000 行会延伸到未来日期标签。这些是边界测试槽，未赋予真实交易日、历史可得性或真实证券行情资格。
- OHLC 使用原始整数分位生成并经过正常精确解析；金额字段按格式生成合成 binary32。研究使用原始查询中的精确价格文本/Decimal，不用平滑价格替换源值。证券与 SH 市场身份为测试声明；所有系列同截止、无缺行，不能代表异常/缺失密集的真实数据分布。
- 导入、建库、应用启动、额外的结果/输入不变性检查、最终重读均在计时外。公式计时包括完整规范化及研究报告构造，单独报告 JSON 编码时间；其输入已加载。产品的逐请求原件校验仍在完整读取和 ASGI 计时内。
- ASGI 计时从客户端发起调用到取得完整响应，包含预算预检、逐请求原件校验、查询、公式和 JSON 序列化。它使用进程内 ASGI transport，没有实际 TCP/网络、压缩、浏览器解析、绘图或用户交互。
- 每项三次，首轮也保留；未做预热丢弃、百分位外推或异常值剔除。导入/前序调用已使数据库和 OS 缓存可能变热；未隔离 CPU，未模拟冷启动或慢磁盘。
- 纯算法查询夹具在 ASGI 前经过不变性检查、释放并执行一次垃圾回收。ASGI 各次之间保留正常 GC 行为。完成后重新读取来源并核对相同精确查询指纹，避免测试框架额外保留 200,000 行对象污染正式接口测量。

## 独立热点剖析

正式计时结束后，另用同一合成生成器对 **2×20,000 行** 做一次 `cProfile`，日志为 `$EVIDENCE_ROOT/anatrading-test-logs/research-profile.log`，复现脚本为同目录 `profile-research.py`。这不是 200,000 行的阶段占比测量；插桩会显著增加 Python 调用成本，以下时间仅用于识别热点，不能替换上表延迟，也不能相加重叠的 cumulative 项。

- 完整查询插桩总计 3.022 秒：80,006 次 JSON `loads` 累计 1.129 秒；240,012 次 `decimal_text` 累计 0.581 秒；DuckDB `fetchall` 0.398 秒；`exact_sum` 0.185 秒；`_quality` 0.121 秒。行对象重建、JSON 解码和重复数值表示转换有明确成本。
- 同规模集合插桩总计 1.974 秒：`daily_bars` 累计 1.651 秒，其中 `decimal_value` 0.882 秒；另有日期、身份冲突、截止过滤和覆盖扫描。热点以完整前缀规范化为主，末尾 253 个价格上的集合统计量没有进入前列。
- 双股 W252 插桩总计 13.077 秒：`_price_statistics` 累计 3.843 秒、`_return_statistics` 2.693 秒，中心化与 `math.fsum` 是重叠的主要子调用。与窗口重算路径一致。
- 剖析后精确查询输入与原件哈希仍保持不变。它与正式性能测量顺序执行，没有同时争用计时 CPU。

## 主要成本与下一步范围

1. **集合优先查完整前缀的物化成本。** 上限集合只返回数十 KiB，但仍加载与检查 200,000 行。分层结果将逐请求原件校验、计数与完整查询分开，不能因请求慢就取消原件校验。现有 `store.query` 还构建所有字段、tokens/checks、质量统计和全部字段精确合计；这些是下一轮剖析与有限优化的候选。研究专用读取若减少多余物化，须先明确并测试来源、NULL、未定位行、原序号、计数与 query_id/导出边界，不改变原查询语义。
2. **集合公式仍遍历整个前缀。** `universe_report` 的覆盖与日期组资格基于完整所选来源，随后才在末尾 W+1 个价格上计算指标。直接只取最后 253 行会丢失覆盖/坏组证据，不能作为等价优化。可单独研究如何复用规范化与覆盖扫描，再用独立参考验证相同成员、分母、排序与失败原因。
3. **双股 W252 的回归窗口有可见计算成本。** 当前中心化窗口重算为 O(TW)，W20→252 会明显增耗。数值稳定性与可审计性已在方案中优先选择；未来若改滚动累计，需要独立中心化参考、定期重基、退化门槛与逐前缀不变性复验，不能直接换成不稳定的相减累计量。
4. **单股/双股完整响应仍较大。** 5k→20k 响应接近四倍，W20→252 体积变化很小，与当前按行输出、没有逐柱复制整个窗口的结构一致。它不证明浏览器绘制流畅；20k 的十余 MiB 响应应继续测浏览器解析/绘图与按可见窗口渲染。源价格继续精确保留，递推初始化继续使用完整前缀。
5. **请求排队影响仍开放。** 当前请求复用 owner 执行器；单个大请求的耗时意味着其他请求可能等待。并发队列、取消、峰值内存、实际本地 HTTP 和 Windows 原生延迟尚未验证。本轮没有添加队列/缓存框架，也没有改产品代码。
