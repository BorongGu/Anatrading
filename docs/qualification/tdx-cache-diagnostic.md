## 三条记录的精度差异

独立按现有 `.day` 布局取出日期、四个报价整数、金额 binary32 和成交量 uint32。12 个 HTTP OHLC 值乘 100 均等于相应报价整数；这是一组格式映射观察，报价单位及复权资格仍执行原合同。

| 日期 | HTTP Volume 减缓存 uint32 | HTTP Volume 等于缓存整数转 binary32 | HTTP Amount × 10,000 减缓存金额的精确 binary32 值 |
|---|---:|---|---:|
| 2026-09-28 | +1 | 是 | −8 |
| 2026-09-29 | +3 | 是 | −32 |
| 2026-09-30 | −1 | 是 | −12 |

**观察事实：** 三条 HTTP 成交量均不等于同日期缓存整数；差值已存在于原始 HTTP 数字字符串，本方解析未将其转为浮点。金额的倍率比较也存在非零尾差。本次审核不得记为逐字段全等通过。

**推论：** 成交量差值与 binary32 量化结果完全一致，支持接口上游曾经过浮点量化的解释。仅凭三条响应和缓存无法定位具体服务端实现，也不能证明缓存整数就是交易所最终真值。金额差异可能涉及不同输出精度／量化；不能从二者恢复未观察到的原始成交金额。

## 对数据处理的决定

1. 当前 TQ HTTP 响应只能作为该请求的行情观察证据，不能直接作为精确成交量主来源。保存字符串也无法修复上游已经丢失的信息。
2. 同版 `.day` 缓存保留原成交量整数与 binary32 金额的精确展开；不以 HTTP 覆盖缓存，不按已见尾差补整数，不合并两种来源成单条“真值”。它是客户端缓存来源，不能标作用户手动导出。
3. 先对这份真实新缓存做独立字段复核，再另定既有格式的离线导入范围；不新增 HTTP 采集器／格式白名单，不开启金额或量能指标。手动导出一致性、原始单位、商业版本、分钟、其他证券和全市场覆盖仍待验。
