## P1：本批必须闭合的门槛

### ICV01 · 中断尝试的持久化起点缺失

- **定位：合同第 53、55、57 行。** 第 55 行只明确在最终事务中提交尝试的终态，第 57 行同时承诺重启后将未提交状态登记为 interrupted；尚未写出此前何时持久化尝试。
- **具体失败例：** 原件已发布，进程在最终事务前或事务内被终止。若尝试仅随最终事务创建，数据库没有该尝试记录，重启无法区分一次中断的导入与无归属的原文件，也无法兑现“登记 interrupted”。
- **最小修改：** 导入开始先单独提交 `attempt_id`、开始时间、输入说明及 in-progress 状态；最终事务原子写批次/快照与该尝试终态。启动恢复只处理没有已提交结果的在途尝试；存在幂等提交结果时恢复为 committed。同内容的新尝试可指向旧批次，不能创建重复快照。无需完整事件溯源系统。
- **验收：** 在“开始记录后”“raw 发布后”“最终事务中”“COMMIT 成功但返回前”四个点终止进程。前三者没有可见解析快照；末者恢复同一已提交结果。尝试状态、快照存在性、重试结果相互一致。
- **门槛：** 尝试/恢复模块编码前补文本，持久化能力启用前执行上述故障测试。

### ICV02 · COMMIT 与取消请求需要单独的接受边界

- **定位：合同第 57、79 行。** “提交成功为线性化点”正确，但没有定义取消何时被接受，以及 COMMIT 已开始但尚未返回时如何回答取消。
- **具体失败例：** 取消检查之后、数据库提交完成之前收到 Ctrl+C 或取消请求；客户端先看见 cancelled，数据库随后保存成功。反向情形是 COMMIT 已生效，返回途中中断后被误记为 interrupted。
- **最小修改：** 单写者串行执行最后一次取消检查；进入提交临界段后不再确认取消成功，返回处理中/取消已来不及，最终由持久化提交结果决定 committed 或 failed。已确认取消的尝试必须没有解析快照；结果不明时先查账本。可以仅为同步 CLI 定义这个行为，不必提前制作异步取消服务。
- **验收：** 取消分别落在接受边界前、临界段中和提交后；检查终态与是否存在快照，尤其验证“取消成功确认”与“提交成功”不能同时成立。
- **门槛：** 取消与提交模块编码前补竞争裁决；对外提供取消前通过测试。

### ICV03 · 离线备份在关闭数据库后仍需排他

- **定位：合同第 49、67 行。** 第二写入进程目前由数据库文件锁约束；正常关闭 DuckDB 后，该约束不能覆盖整个文件复制过程。
- **具体失败例：** 备份关闭数据库并开始复制，此时另一个 CLI 成功打开同一目录、导入或触发 checkpoint。备份可能混入不同时点的数据库、原件引用清单和文件，单文件哈希正确也不足以证明整体同版。
- **最小修改：** 同一数据根目录的导入/备份操作共享一个进程级排他约束，锁跨越关闭数据库、复制和验证全过程。可用一个本地操作锁；无需网络锁或第二数据库。若选择外部离线前提，工具必须能检测并拒绝破坏该前提的第二写者。
- **验收：** 暂停备份在“数据库已关、复制未完成”处，第二写入者须被明确拒绝；恢复到新目录后，核对数据库全部原件引用和冻结查询。故障备份不得标 complete。
- **门槛：** 备份模块编码前定案，宣称首个完整操作链完成前通过。该项不阻断不涉及备份的解析器实现。

### ICV04 · 标签筛选和质量计数尚缺确定的边界

- **定位：合同第 29—31、43—45、63、78 行。** 查询已有快照和模式约束，但未固定截止包含关系、同标签记录次序，以及无法解析时间的行和未执行检查怎样进入质量计数。
- **具体失败例：** 两条同标签记录在不同页面被去重或遗漏；非法时间行因 SQL NULL 筛选消失，截断后的质量统计显示零错误；全批次失败数被误当作截止内失败数。调用方另传与快照不一致的规则版本，也可能导致同快照不同解释。
- **最小修改：** 固定一种明确规则，例如 `parsed_label <= cutoff` 后按 `(parsed_label, source_record_ordinal)` 排序，保留同标签全部记录；源序号界限另说明包含关系。无可解析标签的行保留在“无法定位”清单，不能归入某截止窗口，也不能静默算通过。检查结果区分 pass/fail/not_evaluated 及原因；区间质量计数只针对选中记录，全批次数和无法定位数另名返回。合同/规则版本从快照继承，显式覆盖不一致时拒绝。无需查询语言或通用质量规则引擎。
- **验收：** 同标签双行、边界恰好相等、越界哨兵行、非法标签行、未知单位未评价五类独立用例；查询、JSON/Parquet 导出和对应范围的计数完全一致，两种 PIT 模式继续拒绝。
- **门槛：** 查询与质量输出模块编码前补规则；启用时完成上述用例。

### ICV05 · 数值类型条件接受，实际桥接证据仍是门槛

- **定位：合同第 35—41、65、76、80 行；numeric-observations 第 4 节。** `DECIMAL(38,18)` 与非负 BIGINT 是清楚且有限的表示选择。最初数值观察未执行存储往返；本轮随后收到并核读 numeric-roundtrip 报告：DuckDB 1.5.6 / PyArrow 25.0.1 的 38,763 行逐值往返相等，34 个边界案例按预期允入/拒绝。**独立存储实验的缺证条件已补齐**；它依赖精确前置检查，尚未证明将来的产品写入、API、汇总实现符合合同。
- **需要明确的边界：** DECIMAL 的绝对值上限为 `99999999999999999999.999999999999999999`，量为 `0..9223372036854775807`。有效小数位检查不能先经舍入；纯尾零不构成数值超精度。单值符合范围不保证批次汇总符合相同列范围；汇总需要精确输出或明确失败，不能截断、转浮点或回写成单值字段。
- **最小修改：** 将上述边界、已测依赖版本、实验指纹及“产品入口同样必须精确前检”列入定案记录；保留当前独立源字段/规范字段设计。实验明确显示裸 CAST 会将超精度值舍入、将 `1.5` 股转成 2，不能作为产品验证器。规范股/元生成还需带可核对契约证据，字段单位声明不能越过该条件。
- **最小实验：** 已核样本的精确值；`37.020000457763671875` 数值可存；`1.00000011920928955078125`、`1e-19`、`1e20` 分别按精度/幅度拒绝；类型最大值及其越界；带冗余尾零的等价值；NaN/Infinity、NULL/0；超过 JavaScript 精确整数范围的合法 BIGINT；单值合法但汇总越界。经过 Decimal→数据库→Arrow/Parquet→读回和精确 JSON 后逐值核对，同时保留原有字段状态。数值负例可存不改变其来源或分析资格。
- **门槛：** 候选存储类型与该实验通路可据补证进入实现。此 P1 留在产品数值入口、精确 API 和汇总/导出的启用验收，已有实验不重复扩样；产品仍需证明保留前检与无损传递，不能用实验脚本的通过代替实现测试。未通过的产品导出路径保持未启用。
